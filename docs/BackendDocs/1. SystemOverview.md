# System Overview

## Purpose

Ascent Dashboard is the central platform for Ascent Techfest participants. It handles user identity, event registration, phase-based question-driven submissions, QR validation (food + event entry), and an admin panel for organizers and scanners.

---

## Tech Stack

| Layer     | Technology                                         |
| --------- | -------------------------------------------------- |
| Backend   | Python 3.13, FastAPI, uv                           |
| Database  | Supabase (PostgreSQL) via `supabase-py` async SDK  |
| Auth      | JWT via `python-jose`; separate user + admin flows |
| Frontend  | React 18, Vite, React Router v7                    |
| Dev proxy | Vite proxies `/api/*` → `localhost:8000`           |

---

## Core Responsibilities

1. **User identity** — login, profile, Unstop sync
2. **Event lifecycle** — listing, registration, phase management
3. **Question-based submissions** — per-phase typed question forms with full server-side validation
4. **Access control** — registration check, restriction flag, phase active/locked gates
5. **QR validation** — college entry, event attendance, food meal claims
6. **Admin panel** — stats, participant management, event manager roles, scanner UI

---

## High-Level User Flow

1. User receives credentials (username + password) via Unstop sync
2. Logs in → JWT stored in `localStorage`
3. Dashboard loads registered events from `GET /events` cross-referenced with `users.events`
4. User navigates to an event → sees phase timeline
5. Active phase → submission form loads questions from `GET /events/{id}/questions?phase=N`
6. User fills in typed answers → `POST /events/{id}/submit`
7. Service validates answers, writes to `users.events` then `events.participants`
8. QR codes validate physical attendance and food claims in real time

## Key Design Decisions

### 1. Question-Based Submissions (migration 021)

Submissions are no longer free-form link pairs. Organizers define typed questions per phase (`text`, `text-long`, `url`, `email`, `numeric`, `mcq`, `multi-choice`, `declaration`). The service validates each answer server-side before writing.

### 2. Dual-Write Consistency

Every submission writes `users.events[eventId].submission` first, then `events.participants[userId].submission`. User row first — a failure on the event row leaves a recoverable state.

### 3. Intentional Denormalization

`users.events` = user-centric latest snapshot (fast dashboard reads).  
`events.participants` = event-centric history with scoring slots (`score`, `feedback` — set by admins after judging).

### 4. Phase Gate

Submission is only accepted when the round has `is_active = true` AND `is_locked = false`. The frontend derives UI state (`LIVE` / `UPCOMING` / `LOCKED`) from these two flags.

### 5. Two Independent JWT Flows

- User token → `localStorage.ascent_token` — scopes `/auth/*`, `/users/*`, `/events/*`
- Admin token → `localStorage.ascent_admin_token` — scopes `/auth/admin/*`, `/admin-panel/*`, `/qr/*`

## System Boundaries

| In scope                         | Out of scope            |
| -------------------------------- | ----------------------- |
| Users, events, submissions, QR   | Mirage photo archive    |
| Admin panel, scanner UI          | Sidequest engine        |
| Announcements, ratings, feedback | Campus tour checkpoints |

## Performance Targets

- API response: < 200 ms
- QR scan round-trip: < 300 ms
- Concurrent users: 1 000+
