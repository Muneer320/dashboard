# **User & Event Dashboard: Backend & System Design (Detailed PRD)**

---

## **1\. System Overview**

This system integrates Unstop registrations, internal dashboard management, event participation, and a QR-based validation system into a unified backend.

### **Core Responsibilities**

* User identity synchronization (Unstop \+ internal users)  
* Event lifecycle management  
* Submission handling  
* QR-based validation (food and event entry)  
* Real-time participation tracking

---

## **2\. High-Level Workflow**

### **2.1 User Flow**

1. User registers on Unstop  
2. Upon acceptance:  
   * Receives unique ID and temporary password via email  
3. Backend sync pulls user data → inserts into database  
4. User logs into dashboard  
5. If profile is incomplete → onboarding form is shown  
6. User accesses dashboard and interacts with events

---

### **2.2 Internal System Flow**

* Scheduled job / webhook:  
  * Fetch users from Unstop  
  * Normalize data  
  * Insert/update into `users` table  
* All dashboard interactions:  
  * Read/write operations on `users` and `events` tables

---

## **4\. Authentication & Authorization**

### **Login Flow**

* Username \+ Password  
* Verify password hash  
* Return JWT

---

### **Roles**

* `user` → standard dashboard access  
* `scanner` → QR scanning interface  
* `admin` → event and system control

---

### **Credential Distribution Strategy**

* Credentials (ID \+ password) are issued **once per user** upon their **first successful event registration via Unstop**  
* For subsequent event registrations:  
  * The system checks if the user already exists  
  * No additional credentials are generated

---

### **Access Control Strategy**

* Access is controlled dynamically based on:  
  * Event participation  
  * User-specific access levels  
  * Event phase status

---

### **Access Levels**

| Level | Description |
| ----- | ----- |
| ROUND1 | Access limited to submission and qualification status |
| FINAL | Access to final round features |
| FULL | Access to all dashboard features |

## **6\. QR System Design**

### **QR Content**

{  
  "userId": "UUID"  
}

---

### **Scanner Flow**

#### **Step 1: Select Mode**

* Food  
* Event Entry

---

#### **Step 2A: Food Mode**

* Select meal

**Logic:**

* If meal already consumed → reject  
* Else → mark consumed

---

#### **Step 2B: Event Entry Mode**

* Select event  
* Select venue

**Logic:**

* Verify registration  
* Verify access level  
* Prevent duplicate entry  
* Mark attendance

---

## **7\. Event Registration Flow**

POST /events/:id/register

### **Logic**

* Validate eligibility  
* Validate deadline  
* Validate capacity

### **Updates**

* Insert into `users.events`  
* Insert into `events.participants`

### **Credential Handling**

* Generate credentials only if user does not exist

---

## **8\. Submission Flow**

POST /events/:id/submit

### **Logic**

* Validate phase status  
* Validate submission type  
* Validate user access level

### **Updates**

* Update both:  
  * `users.events`  
  * `events.participants`

---

## **9\. State Control**

### **Phase Control**

* Controlled via:

"is\_active": true  
"is\_locked": false

---

### **Access Enforcement**

* Users can only:  
  * Access phases matching their access level  
  * Submit within active phases  
* Non-registered users:  
  * Limited to viewing event overview

---

## **10\. Data Consistency Strategy**

The system maintains overlapping data structures:

* `users.events`  
* `events.participants`

### **Rationale**

* Optimized read performance  
* Reduced query complexity

### **Consistency Enforcement**

* Use atomic transactions  
* Update both structures simultaneously  
* Periodic integrity validation

---

## **14\. Access Control Model**

The system implements a **per-event access control model**, where permissions are scoped at the event level.

### **Key Characteristics**

* Users may have **different access levels across events**  
* Access is determined by:  
  * Event participation  
  * Event phase  
  * User-specific access level

### **Benefits**

* Fine-grained control over:  
  * Feature visibility  
  * Submission permissions  
  * Phase transitions  
* Eliminates dependency on credential timing for access control  
* Ensures scalability for multi-event participation scenarios
